# CodeBuddy 行为规则

基于 Andrej Karpathy 对 LLM 编码痛点的洞察制定的行为指南，合并到当前 VaultGo（Swift/iOS）项目中使用。

**权衡说明：** 这些规则偏向谨慎而非速度。对于简单任务（如修改单个错别字、一目了然的单行修复），请自行判断适度放宽松。

---

## 1. 思考先于编码 / Think Before Coding

**不要擅自假设。不要隐藏困惑。要主动呈现权衡方案。**

在实现之前：
- 明确陈述你的假设。如果不确定，直接提问。
- 如果存在多种理解方式，把它们列出来——不要默默选一个。
- 如果有更简单的方案，指出来。必要时要敢于反对用户的想法。
- 如果某件事不清楚，停下来。指出哪里困惑，然后问清楚。

## 2. 简洁至上 / Simplicity First

**用最少代码解决问题。不要做任何投机性的提前设计。**

- 不添加用户没有要求的功能。
- 不为单一用途的代码创建抽象层。
- 不添加用户没有要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景添加错误处理。
- 如果你写了 200 行代码但实际上 50 行就能搞定，重写它。

时刻问自己：**"一个资深工程师会觉得这段代码过度复杂吗？"** 如果答案是 yes，简化它。

## 3. 外科手术式修改 / Surgical Changes

**只动必须动的地方。只清理你自己产生的混乱。**

编辑已有代码时：
- 不要"顺手优化"相邻的代码、注释或格式。
- 不要重构没有坏的东西。
- 匹配现有的代码风格，即使你自己会写得不一样。
- 如果注意到不相关的死代码，提出来——但不要删除它。
- 如果是你的修改导致 import/变量/函数不再被使用，要删除它们。
- 不要删除用户修改之前就存在的死代码，除非用户明确要求。

**检验标准：** diff 中的每一行改动，都应该能直接追溯到用户的请求。

## 4. 目标驱动执行 / Goal-Driven Execution

**定义成功标准。循环直到验证通过。**

把模糊任务转化为可验证的目标：
- "加个校验" → 「先写验证失败用例的测试，再让它通过」
- "修一下 bug" → 「先写能复现 bug 的测试，再让它通过」
- "重构 X" → 「确保重构前后测试都通过」

对于多步骤任务，先列出简要计划：
```
1. [步骤] → 验证: [检查方式]
2. [步骤] → 验证: [检查方式]
3. [步骤] → 验证: [检查方式]
```

明确清晰的成功标准能让你独立闭环执行。模糊的标准（如"能跑就行"）则需要不停追问澄清。

---

## 5. VaultGo 项目专属规则

- **语言：** 代码注释使用中文，文档使用中文。
- **架构：** 遵循 MVVM 模式，View 只负责 UI，ViewModel 处理业务逻辑。
- **Swift 并发：** 优先使用 `async/await`，避免回调嵌套；UI 更新必须在 `@MainActor` 上执行。
- **安全性敏感：** 本项目涉及密码管理和加密数据存储，所有安全相关代码必须审慎处理，不要引入安全漏洞。加密、钥匙串操作必须经过验证。
- **依赖注入：** 服务层通过协议抽象，便于测试和替换实现。
- **最小改动原则：** 对现有 `.swift` 文件做修改时，优先使用 `replace_in_file` 做精确替换，避免重写整个文件。

---

## 6. 本地 Git 版本控制 / Local Git

**本项目只使用本地 Git，永不推送到任何远端。**

- **禁止执行** `git remote add`、`git push`、`git fetch`、`git pull`。仓库没有远端，所有历史都存在项目根目录的 `.git/` 中。
- **每完成一轮修改后必须提交一次**，让 AI 的每次改动都成为可回退的版本节点：
  ```bash
  git add -A && git commit -m "<类型>: <简述>"
  ```
  提交信息类型：`feat` / `fix` / `refactor` / `chore` / `docs`，简述用中文。
- 提交前用 `git status --short` 抽查，确保没有把 `spm-packages/`、`DerivedData/`、`xcuserdata/` 等产物带进去。
- **不要**在提交信息里加 `Co-Authored-By` 之类 AI 署名，也不要自动 amend 已有提交。
- 用户要求回退时，优先用 `git log --oneline` 定位版本，再用 `git restore --source=<commit> -- <路径>` 精确还原，不要直接 `git reset --hard`。

---

**这些规则生效的标志：** diff 中无关改动变少、代码一次到位不需要反复精简、问题性提问在实现之前而非犯错之后出现。
